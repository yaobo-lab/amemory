# 《SIP呼叫流程：从拨号到接听的全过程》

## 本篇定位与场景

- **真实场景**：你拿起 phone01（分机 8001）拨同事 8002，听到"嘟…嘟…"回铃音，phone02 振铃，对方摘机通话，挂断归零。
- 从按下号码到接听之间，SIP 服务器与两部话机之间**飞快交换了一串标准化信令消息**。
- **两条主线**：
  - ① SIP 只负责"找人、协商、接通、挂断"（**信令平面**）；
  - ② 真正的声音走独立的 RTP 流（**媒体平面**）。两个平面缺一不可。

---

## 一、一次通话 = 信令 + 媒体 两个平面

拨号 ≠ 直接说话。VoIP 通话像谈合作：先书面磋商（SIP 信令），达成后才打开语音通道（RTP 媒体）。

| 平面 | 职责 | 说明 |
|---|---|---|
| 信令平面（SIP） | 会话"控制" | INVITE 邀请、180 振铃、200 OK 接听、ACK 握手、BYE 结束 |
| 媒体平面（RTP） | "传声" | 真正语音报文。**直连还是经服务器中转由服务器配置决定，并非绝对规则**：同局域网直连或中转都可行（常配直连省资源）；跨 NAT/公网时私网地址不可达易单通，经 SIP 代理/媒体服务器（如 SBC）中转更稳妥 |

### SIP 消息全景（图1）

```
INVITE ──> 100 ──> 180 ──> 200 OK ──> ACK ──> [RTP] ──> BYE ──> 200 OK
发起邀请    尝试中   被叫振铃  被叫接听    确认    语音流    挂断    确认挂断
含SDP offer  防重传  主叫回铃  含SDP answer 开始媒体 (非SIP方法) 任一方   释放
```

> 信令消息（INVITE/100/180/200/ACK/BYE）走 SIP 控制通道；RTP 是独立媒体流，**不属于 SIP 方法**。

**与上一篇《SIP注册流程》衔接**：注册只用 REGISTER 一个方法，呼叫要动用 INVITE、多个响应码、ACK、BYE 一整套"会话控制"。注册解决"服务器找得到你"，呼叫解决"把两个人实时接通"。

### RTP 媒体两种传输方式（图2）

```
场景一：同局域网（点对点直连）
 主叫UA phone01 <── SIP信令 ──> SIP服务器(仅转发信令) <── SIP信令 ──> 被叫UA phone02
 主叫UA phone01 <════════════ RTP直连(不经服务器) ════════════> 被叫UA phone02

场景二：跨NAT/公网（媒体经服务器中转）
 主叫UA phone01 <── SIP信令 ──> SIP服务器/媒体服务器(SBC中转媒体) <── SIP信令 ──> 被叫UA phone02
 主叫UA phone01 <════ RTP ════> SIP服务器/媒体服务器 <════ RTP ════> 被叫UA phone02
```

## 二、三个角色：主叫、被叫、代理

SIP 把通信两端都叫 **UA（User Agent，用户代理）**，按动作分主叫和被叫：

| 角色 | 是什么 | 本例 |
|---|---|---|
| 主叫 UAC | 发起 INVITE 的一方（Client） | phone01（8001） |
| 被叫 UAC | 接收 INVITE 的一方（Client） | phone02（8002） |
| 服务器 UAS | 转发信令、按 Location 表把 INVITE 路由到被叫当前 Contact | company.com |

**与第11篇的衔接**：你拨 8002 时，主叫并不知道 phone02 此刻在哪台设备、哪个 IP。服务器查第11篇讲的 **Location 表**，用 phone02 注册时上报的 Contact 把 INVITE 精准投递过去。**没有注册，呼叫的"最后一公里"就找不到人。**

## 三、呼叫完整过程（本篇核心）

三大阶段：**① 呼叫建立 / ② 通话中 / ③ 会话释放**，按真实顺序共 ①→⑧ 步。

### 图3：模式一 RTP 直连（同局域网）

```
主叫UA phone01        SIP服务器 company.com        被叫UA phone02
     │                       │                          │
①呼叫│── INVITE(SDP offer) ─>│                          │
 建立│                       │── INVITE(SDP offer) ────>│
     │<──── 100 Trying ──────│<──── 100 Trying ─────────│
     │<── 180 Ringing(振铃) ─│<── 180 Ringing(被叫振铃)─│
     │<─ 200 OK(接听,SDP answer)─│<─ 200 OK(接听,SDP answer)─│
     │── ACK(确认,媒体开始) ─>│                          │
     │                       │── ACK(确认,媒体开始) ────>│
②通话│◄═══════════ RTP直连: 主叫 ⇄ 被叫 ═══════════►│
  中 │                                                  │
③会话│────── BYE(挂断) ─────>│                          │
 释放│                       │────── BYE(挂断) ─────────>│
     │<── 200 OK(释放会话) ──│<── 200 OK(释放会话) ──────│
```

### 3.1 逐步拆解（①→⑧）

1. **INVITE + SDP offer**：主叫发出邀请，附上自己的媒体能力（支持的编解码、端口），**经服务器转发给被叫**。
2. **100 Trying**：服务器和被叫各自先回 100（"已收到、在尝试处理、别重发"）——是**逐跳（hop-by-hop）**的临时响应。
3. **180 Ringing**：被叫开始振铃，回 180（经代理给主叫）；主叫据此**本地生成回铃音**（"嘟嘟"声）。
4. **200 OK + SDP answer**：被叫摘机，回 200 并带上选定的媒体参数；主叫收到即知"对方接了"。
5. **ACK**：主叫确认收到 200，三次握手完成，**媒体通道正式打开**。
6. **RTP 语音流**：真正对话。两种走法由服务器配置决定——局域网点对点直连（图3）；跨 NAT/公网经统一 SIP 服务器中转更稳妥（图4）。
7. **BYE**：挂断，发 BYE（经 SIP 服务器转发给对端）。
8. **200 OK**：对端回 200 OK，会话释放。

> **一句话记住**：INVITE 敲门 → 100 说"收到" → 180 说"在响" → 200 说"接了" → ACK 说"好，开始" → RTP 开聊 → BYE 说"再见"。INVITE→180→200 是"邀请三件套"，100 是防重传的临时响应，ACK 是媒体开关，BYE 是礼貌收场。

### 图4：模式二 RTP 经 SIP 服务器转发（跨 NAT/公网）

```
主叫UA phone01         SIP服务器(信令+媒体)         被叫UA phone02
     │   信令阶段与图3相同：INVITE→100→180→200→ACK   │
②通话中│═════ RTP ════>│ [RTP转发] │<════ RTP ═════│
③释放 │── BYE ─>│── BYE ─>│ ；│<─ 200 OK ─│<─ 200 OK ─│
```

## 四、媒体协商：SDP 的 offer / answer 机制

**为什么协商**：两部话机未必支持相同的编解码。**主叫先"报价"（offer）：我支持这些、用这个端口；被叫"还价"（answer）：从你给的里面挑一个、告诉你我的端口。** 交集确定后 RTP 才能互通。

### 图5：SDP 报价-还价

```
主叫 Offer (phone01)                     被叫 Answer (phone02)
┌──────────────────────────────┐ 协商 ┌──────────────────────────────┐
│ v=0                          │ ───> │ v=0                          │
│ o=phone01 112233 IN IP4      │      │ o=phone02 445566 IN IP4      │
│   192.168.1.100              │      │   192.168.1.101              │
│ c=IN IP4 192.168.1.100       │      │ c=IN IP4 192.168.1.101       │
│ m=audio 20000 RTP/AVP 0 8 101│      │ m=audio 30000 RTP/AVP 0 101  │
│ a=rtpmap:0  PCMU/8000        │      │ a=rtpmap:0  PCMU/8000        │
│ a=rtpmap:8  PCMA/8000        │      │ a=rtpmap:101 telephone-event │
│ a=rtpmap:101 telephone-event │      │        /8000                 │
└──────────────────────────────┘      └──────────────────────────────┘
        共同支持 = G.711 μ律(PCMU) → 选定它
  结果: RTP流 192.168.1.100:20000 ⇄ 192.168.1.101:30000, 编码 G.711 μ律
```

**举例**：phone01 的 offer 说自己能讲 **G.711U（0）、G.711A（8）、DTMF 事件（101）**，监听端口 **20000**；phone02 的 answer 从中挑了双方都有的 **G.711U + DTMF**，并告诉主叫自己端口是 **30000**。于是语音在 192.168.1.100:20000 ⇄ 192.168.1.101:30000 间流动。

**失败场景**：若双方**没有共同编解码**，被叫回 **488 Not Acceptable**，呼叫失败——这正是企业网要统一语音编解码策略的原因。

## 五、振铃与回铃音：180、200 和 183 的区别

拨号后听到的"嘟嘟"声从哪来？涉及三个易混淆消息：

| 消息 | 含义 | 回铃音从哪来 |
|---|---|---|
| **180 Ringing** | 被叫正在振铃的通知 | 主叫话机**本地生成**"嘟嘟"声 |
| **183 Session Progress** | 早期媒体（带 SDP） | 可直接播放**网络侧真实回铃音/提示音**（如"您拨打的电话已关机"） |
| **200 OK** | 被叫摘机接听 | 回铃音停止，进入通话 |

简单说：**180 让你"以为"对方在响，183 让你"听到"对方网络里真实的提示音。** 运营商放音（欠费、空号）就是通过 183 早期媒体实现的。

### 图6：主叫与被叫状态机

```
主叫侧                          被叫侧
[主叫·空闲]                     [被叫·空闲]
    │ 发INVITE                      │ 收INVITE
    ▼                               ▼
[Dialing 拨号中]                [Ringing 振铃中]
    │ 收180/183                     │ 用户摘机 → 200 OK
    ▼                               ▼
[Alerting 回铃中]                   
    │ 收200 → ACK                   │
    ▼                               ▼
[Connected 通话中] ◄══ RTP媒体 ══► [Connected 通话中]
```

**时序细节补充**：被叫话机收到 INVITE 后，**先回 100 Trying（"请求已收到，马上振铃"），然后才回 180 Ringing**——"100 在前、180 在后"是标准顺序。

## 六、排错实战：拨不通、听不到、突然断

### 图7：呼叫故障地图——三处最易出问题的"热点"

```
主叫UA phone01 ──INVITE──> [热点①] 代理company.com ──INVITE──> 被叫UA phone02
              <──200 OK── [热点③]                <──200 OK──
              ············ [热点②] RTP语音流(直连) ··············>

① 无回铃：INVITE未达代理 / 被叫未注册(404) / 被叫忙(486)
② 单通/无媒体：NAT或防火墙阻断RTP端口（媒体直连的锅）
③ 通话中断：Session Timer超时 / ACK丢失 / NAT映射过期
```

### 对症表

| 症状 | 常见原因 | 对策 |
|---|---|---|
| 拨号后**无回铃** | INVITE 未达代理（DNS/网络）；被叫未注册（404）；被叫忙（486）；防火墙拦 SIP | 查网络/代理可达性；确认被叫已注册；检查 SIP 端口 5060 |
| 有回铃但**听不到对方/单通** | RTP 端口被防火墙/NAT 阻断（单向媒体）；SDP 携带私网地址 | 放行 RTP 端口范围；STUN/TURN/ICE；SIP ALG 或媒体走代理 |
| 通话**几秒自动断** | Session Timer 未刷新；ACK 丢失；NAT 映射超时 | 开启 Session Timer；NAT 保活/STUN 心跳；排查 ACK 路径 |
| 能打通但**杂音/断续** | 编解码重协商；链路丢包；QoS 未保障 | 统一编解码；参考第06篇做 QoS 优先级 |

> **重点提醒**：**媒体直连 + NAT = 单通/无媒体的经典元凶。** 若 RTP 配置为点对点直连，一旦某方在 NAT 后、SDP 里填的是私网地址，对端语音包就会被 NAT 丢弃。对策与第04篇 NAT 穿透一脉相承：**STUN 保活、TURN 中继、ICE 打通，或让媒体经语音网关/代理（B2BUA）透传**。

## 七、小结：记得住的一次呼叫

五句话串起本篇：

1. **两个平面**：信令走 SIP（INVITE/180/200/ACK/BYE），媒体走 RTP（直连）；
2. **谁来牵线**：代理查 Location 表，把 INVITE 路由到被叫 Contact（靠第11篇注册）；
3. **邀请三件套**：INVITE → 180（响）→ 200（接）→ ACK（开媒体）；
4. **媒体要协商**：SDP offer/answer 敲定编解码与端口，无交集则 488；
5. **故障看三处**：无回铃看信令、单通看媒体、中断看保活。

### 消息速查表

| 消息/概念 | 一句话 |
|---|---|
| INVITE | 发起呼叫邀请，携带 SDP offer |
| 100 Trying | 逐跳临时响应，防主叫重传 |
| 180 Ringing | 被叫振铃，主叫据此本地回铃 |
| 183 Session Progress | 早期媒体，可放真实回铃音/提示音 |
| 200 OK | 被叫接听，携带 SDP answer |
| ACK | 确认 200，媒体通道正式打开 |
| BYE / 200 OK | 任一方挂断，释放会话 |
| RTP + SDP | RTP 传声，SDP 协商编解码与端口 |

**承上启下**：本篇讲"如何把一通电话打通"。通话中还有一堆花式操作——**保持（Hold）、前转（Forward）、转移（Transfer）、会议（Conference）**，本质上都是在已建立的会话上用 **Re-INVITE / REFER** 等扩展消息"改装"通话。下一篇《通话保持：暂停不打断的奥秘》先讲最基础的 Hold。
