# UDP 广播设备发现排障指南

## 1. 适用场景

本文用于排查以下现象：

- 两台设备可以互相 `ping` 通；
- 两台设备都能抓到本机发出的 UDP 设备发现报文；
- 两台设备都抓不到对方发出的设备发现报文；
- 或者能够抓到报文，但应用没有发现对方设备。

> 当前设备发现使用的是 **UDP 广播**，不是 UDP 组播。
>
> - 广播目标：`255.255.255.255:8585`
> - 组播地址通常位于 `224.0.0.0/4`

## 2. 当前设备发现流程

相关代码：

- `src/business/link/intercom.c`
- `src/business/link/transport.c`
- `src/business/link/link_def.h`
- `src/business/intercom/signaling/local.c`

端口定义：

```c
#define LINK_UDP_PORT_LINK 8585
```

设备 A 发起搜索时：

```text
设备 A → 255.255.255.255:8585
Topic: custom/talk/indoor/device/search
```

设备 B 收到搜索请求并校验成功后，向设备 A 单播回复：

```text
设备 B → 设备 A IP:8585
Topic: custom/talk/indoor/device/search_reply
```

因此完整发现过程是：

```text
设备 A 发送 UDP 广播搜索
          ↓
网络设备转发二层广播
          ↓
设备 B 收到并解析搜索请求
          ↓
设备 B 校验 spaceCode
          ↓
设备 B 向设备 A 单播回复
          ↓
设备 A 接收并处理搜索结果
```

周期搜索采用“每轮发送 2 个请求，之后冷却约 5 分钟”的策略，两个请求间隔约 500 ms：

```c
SEARCH_MAX_REQ_COUNT = 2,
SEARCH_INTERVAL_MS = 5 * 60 * 1000,
```

## 3. Ping 通能证明什么

`ping` 通只能证明：

- 两台设备之间存在 ICMP 单播通信路径；
- IP 地址和基础网络路由基本可用。

`ping` 通不能证明：

- UDP 一定能通过；
- UDP 8585 端口一定能通过；
- `255.255.255.255` 广播一定会被转发；
- 两台设备一定处于同一个二层广播域；
- 应用已经监听并成功处理 UDP 8585；
- 双方的 `spaceCode` 等业务字段一致。

网络设备可以允许 ICMP 和普通单播，同时过滤广播报文。

## 4. 常见原因

### 4.1 抓包过滤条件错误

常见错误包括：

- 使用了示例 IP，而不是设备实际 IP；
- 在设备 A 上过滤了 A 自己的源 IP，却误以为是在查看设备 B；
- 只过滤本机目标 IP，导致漏掉目标为 `255.255.255.255` 的广播；
- 使用 `-Q in` 或 `-Q out` 时，设备上的 `tcpdump` 对方向支持不完整；
- 在错误的网络接口上抓包。

排查时应先使用宽松条件：

```sh
tcpdump -i any -nn -e -tttt -s 0 -vv -A 'udp dst port 8585'
```

确认报文后，再逐步增加源 IP、目标 IP和方向条件。

### 4.2 广播从错误的网络接口发出

设备存在多个网口、网桥或虚拟接口时，`255.255.255.255` 可能从非预期接口发出。

检查广播路由：

```sh
ip route get 255.255.255.255
```

正常示例：

```text
broadcast 255.255.255.255 dev eth0 src 192.168.0.181
```

这表示广播将从 `eth0` 发出，源 IP 为 `192.168.0.181`。

### 4.3 两台设备不在同一二层广播域

即使 IP 地址看起来相近，两台设备仍可能位于：

- 不同 VLAN；
- 不同网桥；
- 不同访客网络；
- 不同无线 SSID；
- 被端口隔离的交换机端口。

检查到对端的路由。假设对端 IP 为 `192.168.0.182`：

```sh
ip route get 192.168.0.182
```

同一二层网络通常应显示：

```text
192.168.0.182 dev eth0 src 192.168.0.181
```

如果出现 `via 网关IP`：

```text
192.168.0.182 via 192.168.0.1 dev eth0
```

说明数据需要经过网关。受限广播 `255.255.255.255` 默认不会被路由器转发到另一个子网。

还可以检查邻居表：

```sh
ip neigh show 192.168.0.182
```

### 4.4 路由器、AP 或交换机过滤广播

这是“Ping 正常、单播正常、广播收不到”最常见的原因。

重点检查以下配置：

- AP Isolation；
- Client Isolation；
- 无线客户端隔离；
- 终端隔离；
- WLAN/LAN 隔离；
- 访客网络隔离；
- 交换机端口隔离；
- VLAN 或 Private VLAN；
- 广播抑制；
- 广播风暴控制；
- 网桥防火墙；
- 交换机 ACL。

如果设备通过 `eth0` 接入，优先检查 VLAN、交换机端口隔离、广播抑制和网桥防火墙。

### 4.5 网络设备不转发 `255.255.255.255`

当前代码使用受限广播地址：

```text
255.255.255.255
```

部分网络设备会过滤该地址，但可能允许接口所在子网的定向广播地址，例如：

```text
192.168.0.255
```

查看接口 IP、掩码和广播地址：

```sh
ip -4 addr show dev eth0
```

示例：

```text
inet 192.168.0.181/24 brd 192.168.0.255
```

只有在确认网络确实过滤 `255.255.255.255` 后，才考虑测试或改用接口实际广播地址。不能在不知道子网掩码时直接假设广播地址一定是 `.255`。

### 4.6 设备自身防火墙过滤 UDP

检查 iptables：

```sh
iptables -L INPUT -n -v
iptables -L OUTPUT -n -v
```

如果系统使用 nftables：

```sh
nft list ruleset
```

一般情况下，`tcpdump` 在物理接口上可以先于主机防火墙看到进入的报文：

- 物理接口完全抓不到：优先检查网络链路、AP、交换机和 VLAN；
- 物理接口能抓到，但应用收不到：检查防火墙、Socket 和应用处理。

### 4.7 应用未监听 UDP 8585

检查监听状态：

```sh
ss -ulnp | grep ':8585'
```

如果系统没有 `ss`：

```sh
netstat -anu | grep ':8585'
```

抓包能看到报文到达，不等于应用一定已经读取报文。还需要确认：

- UDP 8585 Socket 创建成功；
- Socket 绑定地址和端口正确；
- 接收线程正常运行；
- 接收缓冲区和消息解析没有失败。

### 4.8 应用收到报文但业务层忽略

设备 B 收到搜索请求后，还会执行应用层校验。以下问题可能导致不回复：

- Topic 不正确；
- JSON 格式错误；
- `form` 字段缺失或 IP 错误；
- `objects` 字段缺失；
- `spaceCode` 缺失；
- 两台设备的 `spaceCode` 不一致；
- 回复目标 IP 错误；
- 搜索回调没有注册或没有执行。

当前代码在 `spaceCode` 不一致时会忽略请求，并输出类似日志：

```text
接收到搜索指令，空间信息不匹配，忽略
```

## 5. 标准定位步骤

以下示例假设：

```text
设备 A：192.168.0.181
设备 B：192.168.0.182
接口：eth0
端口：8585
```

请根据实际环境替换 IP 和接口名称。

### 步骤 1：确认两台设备的地址和掩码

两台设备分别执行：

```sh
ip -4 addr show dev eth0
ip route
```

确认：

- IP 地址不冲突；
- 子网掩码符合预期；
- 接口状态正常；
- 广播地址符合预期。

### 步骤 2：确认基础单播连通

设备 A：

```sh
ping -c 4 192.168.0.182
```

设备 B：

```sh
ping -c 4 192.168.0.181
```

如果 Ping 不通，应先解决基础网络问题，不继续排查应用层发现流程。

### 步骤 3：确认对端是否为直连路由

设备 A：

```sh
ip route get 192.168.0.182
ip neigh show 192.168.0.182
```

设备 B：

```sh
ip route get 192.168.0.181
ip neigh show 192.168.0.181
```

如果路由经过网关，`255.255.255.255` 不会跨子网转发。

### 步骤 4：确认广播的发送接口

设备 A：

```sh
ip route get 255.255.255.255
```

预期类似：

```text
broadcast 255.255.255.255 dev eth0 src 192.168.0.181
```

设备 B 也执行相同命令，确认使用预期接口和源 IP。

### 步骤 5：在物理接口确认设备 A 发出广播

设备 A：

```sh
tcpdump -i eth0 -Q out -nn -e -tttt -s 0 -vv -A \
'udp src host 192.168.0.181 and dst host 255.255.255.255 and dst port 8585'
```

如果 `tcpdump` 不支持 `-Q out`，使用：

```sh
tcpdump -i eth0 -nn -e -tttt -s 0 -vv -A \
'udp src host 192.168.0.181 and dst host 255.255.255.255 and dst port 8585'
```

应看到类似：

```text
192.168.0.181.xxxxx > 255.255.255.255.8585
```

链路层目标 MAC 应为：

```text
ff:ff:ff:ff:ff:ff
```

负载中应能看到：

```text
custom/talk/indoor/device/search
```

### 步骤 6：在设备 B 确认是否收到设备 A 的广播

设备 B：

```sh
tcpdump -i eth0 -nn -e -tttt -s 0 -vv -A \
'udp src host 192.168.0.181 and dst host 255.255.255.255 and dst port 8585'
```

这里建议暂时不使用 `-Q in`，避免设备上的 `tcpdump` 对方向支持不完整。

结果判断：

- A 能在 `eth0` 看到发出，B 完全看不到：广播在网络中间被丢弃；
- B 能看到：网络广播正常，继续检查应用监听和业务处理。

### 步骤 7：反向验证设备 B 到设备 A

设备 A：

```sh
tcpdump -i eth0 -nn -e -tttt -s 0 -vv -A \
'udp src host 192.168.0.182 and dst host 255.255.255.255 and dst port 8585'
```

触发设备 B 发起搜索，确认反向广播是否到达。

### 步骤 8：测试 UDP 单播

Ping 只测试 ICMP，需要额外确认 UDP 单播。

设备 B 抓取测试端口：

```sh
tcpdump -i eth0 -nn -tttt -s 0 -vv -A \
'udp src host 192.168.0.181 and dst port 9999'
```

设备 A 发送 UDP 单播：

```sh
echo udp-test | nc -u -w 1 192.168.0.182 9999
```

设备 B 不需要真正监听 9999，`tcpdump` 仍然可以观察报文是否到达。

结果判断：

- UDP 单播能到达、广播不能到达：网络侧广播过滤；
- UDP 单播也不能到达：检查 UDP 防火墙、ACL 和网络策略；
- UDP 单播和广播都能到达：检查 UDP 8585 监听及应用处理。

### 步骤 9：检查 UDP 8585 监听和防火墙

```sh
ss -ulnp | grep ':8585'
iptables -L INPUT -n -v
```

如果没有 `ss`：

```sh
netstat -anu | grep ':8585'
```

### 步骤 10：检查应用日志和业务字段

确认：

- 接收回调被调用；
- Topic 是搜索请求或搜索回复；
- JSON 能够正常解析；
- `form` 是正确的发起设备 IP；
- 两台设备的 `spaceCode` 一致；
- B 发出的回复目标为 A 的实际 IP，目标端口为 8585；
- A 能抓到 B 发出的单播回复。

设备 A 查看来自设备 B 的回复：

```sh
tcpdump -i eth0 -nn -e -tttt -s 0 -vv -A \
'udp src host 192.168.0.182 and dst host 192.168.0.181 and dst port 8585'
```

## 6. 结果判断矩阵

| 现象 | 结论或优先检查方向 |
|---|---|
| Ping 不通 | IP、掩码、路由、接口或基础网络问题 |
| Ping 通，UDP 单播不通 | UDP 防火墙、ACL、端口策略或抓包条件问题 |
| UDP 单播通，UDP 广播不通 | AP/交换机广播过滤、VLAN、端口隔离或广播抑制 |
| 发送端仅在 `any` 上看到，物理接口看不到 | 路由、接口绑定或本机网络栈问题 |
| 发送端物理接口看到，对端物理接口看不到 | 中间网络设备未转发广播 |
| 对端物理接口看到，应用监听不到 | 主机防火墙、Socket 绑定或接收线程问题 |
| 应用收到搜索请求但没有回复 | Topic、JSON、`spaceCode` 或回调处理问题 |
| 对端发出单播回复，本机抓不到 | 网络、防火墙或回复目标 IP 错误 |
| 本机抓到单播回复，但界面没有设备 | 搜索回复解析、设备入表或 UI 状态同步问题 |

## 7. 推荐的最小抓包组合

设备 A 确认自己发出：

```sh
tcpdump -i eth0 -nn -e -tttt -s 0 -vv -A \
'udp src host 192.168.0.181 and dst port 8585'
```

设备 B 确认收到 A：

```sh
tcpdump -i eth0 -nn -e -tttt -s 0 -vv -A \
'udp src host 192.168.0.181 and dst port 8585'
```

设备 A 确认收到 B：

```sh
tcpdump -i eth0 -nn -e -tttt -s 0 -vv -A \
'udp src host 192.168.0.182 and dst port 8585'
```

需要保存为 Wireshark 文件时：

```sh
tcpdump -i eth0 -nn -s 0 -U -w /tmp/intercom-discovery.pcap 'udp port 8585'
```

按 `Ctrl+C` 停止抓包，然后将 `/tmp/intercom-discovery.pcap` 复制到电脑上分析。

## 8. 最终结论原则

如果已经确认：

1. 两台设备可以互相 Ping；
2. 两台设备之间 UDP 单播可以到达；
3. 两台设备都能在各自物理接口看到本机发出的 `255.255.255.255:8585`；
4. 两台设备都无法在物理接口看到对方发出的广播；

则可以基本确定：

> 应用发送逻辑和设备本机路由基本正常，问题位于两台设备之间的二层网络，优先检查 VLAN、端口隔离、广播抑制、AP 客户端隔离、网桥防火墙或网络设备对 `255.255.255.255` 的过滤策略。

如果接收设备的物理接口已经能够抓到广播，但应用仍未发现设备，则问题不再是网络转发，应继续检查 UDP 8585 监听、主机防火墙、报文解析、`spaceCode` 校验和搜索回复处理逻辑。
