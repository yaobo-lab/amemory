# QoS服务质量：让语音通话不再卡顿

> 系列学习 · VoIP 实战派 · 本篇标题即对话名称：**《QoS服务质量：让语音通话不再卡顿》**

---

## 0. 引入场景：为什么电话会突然"电音"？

```
场景还原：
  公司例会 IP 话机 conference 通话中
  → 有人开始从网盘下载 20GB 大文件
  → 声音立刻变"电音"、卡顿、断续、听不清
  → 挂电话后一切正常

根因：
  语音和数据挤在同一根网线、同一个出口，
  没有任何排队规则（FIFO 先到先得），
  大流量下载"霸占"全部带宽，语音包只能排队甚至被丢弃。
```

**解决钥匙 = QoS（Quality of Service，服务质量）**：给网络流量定规矩，让重要的语音包"插队"先走，把有限带宽留给最不能等的业务。

## 一、为什么要 QoS？语音的"娇贵"天性

### 1.1 语音流量的四大特征

> 核心认知：语音卡顿**不是带宽问题，而是优先级问题**。

```
┌──────────────────────────────────────────────────────────┐
│ ① 实时性极强  单向延迟 >150ms 感觉"对不上嘴型"             │
│               >400ms 基本无法正常对话（ITU-T G.114 建议）  │
│ ② 抖动敏感    语音包本应每 20ms 准时到达，                 │
│               忽快忽慢 → 声音断续                          │
│ ③ 丢包敏感    丢几个包 = "咔哒"杂音/断字                   │
│               （不像网页丢包能重传）                        │
│ ④ 小包高频规律 每 20ms 一个包（G.711 每包约 200 字节）     │
│               要的是"稳"，不是"多"                          │
└──────────────────────────────────────────────────────────┘
```

**带宽账本（一路语音占多少带宽）：**

| 编码 | 特点 | 带宽/路 |
|---|---|---|
| G.711 | 音质最好 | 约 80~100 kbps |
| G.729 | 省带宽 | 约 8~24 kbps |

> 例：100 人同时开会的外线全用 G.711 → 预留 100 × 100kbps × 1.2 ≈ **12 Mbps**，QoS 要确保这 12M 任何时候都"优先通过"。

### 1.2 没有 QoS 会怎样？

```
        同一根 100M 出口：有人下电影 + 有人打电话

   无 QoS                            有 QoS
┌────────────────────────┐    ┌────────────────────────┐
│ 网络出口（单一队列FIFO）│    │ 网络出口（多队列+预留） │
│                        │    │                        │
│ ██████ 数据(占满) █████│    │ ██语音(优先20%)██      │
│ █ 语音(被挤在后面)     │    │ ██████ 数据(80%) ██████│
│                        │    │                        │
│ 语音排队/被丢弃         │    │ 语音包始终优先出队      │
│        ↓               │    │        ↓               │
│ 卡顿 · 断续 · 杂音      │    │ 流畅 · 清晰 · 不卡      │
└────────────────────────┘    └────────────────────────┘
```

## 二、语音的三道坎：延迟、抖动、丢包

### 2.1 延迟（Latency）

```
单向总延迟 = 传播时延 + 传输时延 + 处理时延 + 排队时延
            (光纤/电缆)  (打包上链路) (设备转发)  (拥塞时暴涨 ★QoS 主战场)

标准：<150ms 优 / <400ms 可接受
```

### 2.2 抖动（Jitter）

```
发送端（等间隔）： ●──20ms──●──20ms──●──20ms──●   间隔均匀
接收端（实际）：   ●●────●●────────●●───────●     间隔乱了 → 断续

对策：抖动缓冲 Jitter Buffer
  接收端先缓存 → 再匀速播放，吸收波动
  ⚖ 缓冲太小抗不住抖动，太大又增加延迟 → 需平衡
```

### 2.3 丢包（Packet Loss）

```
成因： 队列满 → 尾丢弃  |  链路误码
补救： PLC（丢包掩盖，用相邻采样推断）/ FEC（前向纠错，多传冗余包）
      —— 都是"打补丁"，源头不丢才是正道

目标： 丢包率 < 1%（理想 < 0.5%）；>1% 明显杂音，>3% 基本没法听
```

## 三、DiffServ 与 DSCP：给数据包"贴标签"

### 3.1 为什么用 DiffServ

- **IntServ（综合服务）**：每个流都要提前申请预留 → 太重、难扩展。
- **DiffServ（区分服务）** ✅ 主流：不做逐流预约，把流量分几大类（加急/保证/普通），同类统一对待，简单可扩展，特别适合 VoIP。

### 3.2 IP 头里的 DSCP：6 个比特位

```
 IP 头 DS 字段（原 TOS 字节，共 8 位）：
 ┌───┬───┬───┬───┬───┬───┬───┬───┐
 │ 1 │ 0 │ 1 │ 1 │ 1 │ 0 │ 0 │ 0 │
 └───┴───┴───┴───┴───┴───┴───┴───┘
 bit7                     bit1 bit0
 └──── DSCP（0~63）────┘   └ ECN ┘
   101110 = 十进制 46 = EF（语音）   显式拥塞通知
```

### 3.3 PHB：三种逐跳行为

```
┌──────────────────────────────────────────────────────────┐
│ EF 加速转发  DSCP 46(101110)  语音专用：最低延迟/抖动/丢包 │
│              相当于快递"特急件"                            │
│ AF 保证转发  DSCP 10~38(AF11~AF43)  视频/重要数据          │
│              4 大类(AF1~AF4) × 每类 3 个丢弃优先级，        │
│              拥塞时优先丢低优先级的                         │
│ BE 尽力而为  DSCP 0           默认流量，无保障              │
└──────────────────────────────────────────────────────────┘
```

### 3.4 链路层优先级：802.1p（CoS）

```
二层：802.1Q Tag 的 3-bit PRI 字段（0~7）= CoS
      CoS 5 = 语音

 CoS 5  ↔  DSCP 46（EF）  ← 同一优先级的两种说法
 二层交换机看 CoS，三层路由器看 DSCP，跨层需做映射

 CoS 常见映射：0尽力/1背景/2优先生效/3多媒体/4视频/5语音/6语音控制/7网络控制
```

## 四、QoS 工具箱：分类 → 标记 → 入队 → 调度

```
 ① 分类          ② 标记           ③ 入队          ④ 调度
 认出语音流  →   打优先级标签  →   放入优先队列 →   优先发送
 端口/VLAN/MAC   DSCP EF / CoS 5   LLQ 队列        语音先走
```

### 4.1 分类（Classification）
识别依据：**UDP 端口**（SIP 5060/5061、RTP 媒体端口）、**源/目的 MAC**（话机）、**VLAN**（语音 VLAN）、**包内已有 DSCP**。识别越精确，QoS 越精准。

### 4.2 标记（Marking）与信任边界

```
① 话机自标：出厂自打 DSCP EF —— 简单但不可控（可被伪造抢占带宽）
② 交换机重标（推荐）：接入交换机"不信任"终端，
   先清空入向标签，再按"语音 VLAN / 话机 MAC"重新打 EF
   —— 更安全、集中可控
```

### 4.3 队列与调度算法对比

| 算法 | 原理 | 适合语音吗 |
|---|---|---|
| FIFO | 单一队列，无优先 | 否（默认，会被数据挤） |
| PQ 纯优先级 | 高优先级空了才发低的 | 快，但可能饿死其他流量 |
| WRR 加权轮询 | 按权重轮流发送 | 公平，但语音延迟不绝对最小 |
| CBWFQ | 按类分配带宽份额 | 较好，可按业务隔离 |
| **LLQ 低延迟队列** | PQ + 带宽上限 | **最佳（语音首选）** |

### 4.4 拥塞避免 & 监管整形

- **拥塞避免**：默认"尾丢弃"会引发 TCP 全局同步 → 用 **WRED**（加权随机早期检测），拥塞前随机丢少量包，平滑过渡。
- **Policing（监管）**：超速率就丢包/降标（硬限制）。
- **Shaping（整形）**：超速率就缓存平滑（软限制）。

## 五、语音 QoS 实战：端到端保障

**一句话核心：边缘打标 + 中间信任 + 出口优先。**

### 5.1 端到端部署思路

```
            ┌──信任边界──┐
 IP话机  →  接入交换机  →  出口路由器   →  WAN
 自身标记    信任/重标记     LLQ优先队列     保证语音
 DSCP EF46   CoS5→DSCP EF   预留语音带宽    20%带宽

 ① 话机源头打标 EF（或由交换机基于语音 VLAN 重标，更可控）
 ② 中间设备"信任"标记并透传，不在中途清零
 ③ 出口对语音队列做 LLQ + 带宽预留，拥塞时语音优先
 全程无需改动应用层，网络设备按标签自动保障
```

### 5.2 LLQ：语音调度最佳实践

LLQ = 在 CBWFQ 中嵌一个给语音的优先级队列（PQ），**但设带宽上限（如 20%）**——语音"插队但不霸道"。

```
 语音队列 (LLQ Priority)  DSCP EF · 最高优先 · 上限20%（防饿死）┐
 视频/信令队列 (AF·WRR)   DSCP AF · 加权轮询 · 保证份额 ─┼→ [调度器] → [出接口]
 数据队列 (BE)            DSCP 0  · 默认 · 剩余带宽     ┘  语音优先   语音先发
                                                            空了再轮询  稳定不卡
 对比：PQ = 语音永远先走 → 高流量时饿死数据/视频
       LLQ = 优先但限速 → 既低延迟又不饿死其他 ✅
```

### 5.3 带宽预留计算

```
公式： 并发路数 × 单路带宽 × 1.2（协议开销） = 需预留带宽

示例： 峰值 50 路并发 × G.711(约100kbps) × 1.2 ≈ 6 Mbps
      出口 100M → 给语音队列预留 6~10M，其余给数据
```

### 5.4 WiFi 环境：WMM

无线更"乱"更要做 QoS。**WMM（WiFi Multimedia，802.11e）** 分 4 个接入类别：

```
优先级： AC_VO(语音) > AC_VI(视频) > AC_BE(尽力) > AC_BK(背景)
开启 WMM 后，无线 AP 优先调度语音帧，避免无线拥塞卡掉电话
```

## 六、排错实战：配了 QoS 还卡怎么办？

> 多半是"标签断链"——某一环没生效。

```
排错四步：
① 语音包被打标了吗？
   话机/交换机抓包，看 IP 头 DSCP 是否 46(EF)；
   若为 0(BE) → 检查话机配置或交换机重标规则
② 中间被清零了吗？
   有设备默认"不信任"入向标记会把 DSCP 重置为 0
   → 沿途每台设备检查是否配置 trust dscp
③ 出口配了优先队列吗？
   确认 LLQ/priority 配置存在，预留带宽按并发路数算够
④ 物理链路达标吗？
   QoS 救不了带宽本身不足或延迟过高的链路
   → 先 ping / 测速确认底层质量
```

**⑤ 抓包实证（把"卡"量化出来）：**

```
第一步：关键位置抓包
  · 话机侧：IP 话机 Web 管理页自带抓包，导出 pcap
  · 网络侧：交换机端口镜像(SPAN)复制流量，电脑 Wireshark 抓
  · 服务器端：SIP 服务器网卡直接抓
  过滤 RTP：udp.port == 5004 或直接输入 rtp

第二步：看三个硬指标（Wireshark: 电话→RTP→流分析）
  · 丢包：看 RTP 序列号是否连续（101、102、「104」→ 丢了一个）
          流分析直接给出 Lost（丢包数/丢包率）
  · 抖动：看每包到达间隔(Delta)与累计抖动(Jitter)，
          面板给出平均/最大抖动
  · 语音质量：MOS / R-Factor 直接给分，对照 MOS 标准

判定与定位：
  丢包率 > 1% 或平均抖动 > 30ms → 基本就是"卡"的元凶
  对比话机侧与服务器侧同通话抓包：
    两边都丢 → 终端/接入问题
    只有一侧丢 → 问题在中间网络（汇聚、防火墙、WAN）
```

QoS 一句话：给流量定规矩，让语音包"插队"先走
│
├─ 为什么：语音四特性（实时/怕抖/怕丢/小包规律），卡是优先级问题

│        无线加 WMM(AC_VO 最高)
└─ 排错：打标? → 清零? → 优先队列? → 物理链路? → 抓包看序列号/抖动/MOS
