# 《802.1X认证：网络准入的第一道门》（乘风VoIP实战派）

## 引子：一个被忽视的安全漏洞

- **真实场景**：访客随便找个工位插上网线，立刻拿到内网 IP，直接访问了财务服务器和 VOIP 话机管理后台；更糟的是有人接一台"小盒子"在交换机上，悄悄抓取所有经过的话机 SIP 注册密码。
- **问题根源**：网络没有"准入控制"——只要物理上能插网线（或连 Wi-Fi）就能进网络，如同大楼门禁形同虚设。
- **802.1X 的定位**：在交换机端口上装一道"门禁"，任何设备想上网，必须先证明"我是谁、我有权限"，认证通过才放行。

## 一、802.1X 是什么？——端口级的"门禁系统"

### 1.1 一句话定义
- 802.1X 是 IEEE 制定的**"基于端口的网络接入控制"**（Port-Based Network Access Control）标准。
- 它**不负责加密通信**，只负责**"谁可以接入网络"**——在设备拿到 IP、访问任何资源之前，先完成身份认证。
- **生活类比**：交换机端口 = 公司大门。没装 802.1X = 大门敞开谁都能进；装了 802.1X = 门口有闸机，必须刷工牌（认证）才能过闸，否则只能待在"访客等候区"（隔离 VLAN）。

### 1.2 为什么 VOIP 场景特别需要它？

| 风险 | 后果 |
|---|---|
| 非法话机接入 | 免费打电话、盗打国际长途，话费损失 |
| 抓包窃听 | SIP 密码、通话内容被窃听（甚至可重放注册） |
| 伪造话机 | 冒充他人分机，进行社会工程诈骗 |
| 中间人攻击 | 通话被录音、篡改或重定向 |

结论：让每台话机"持证上岗"，是 VOIP 安全的**第一道防线**。

```
 无 802.1X（大门敞开）                 有 802.1X（闸机门禁）
 ┌──────────────┐                 ┌──────────────┐
 │ 非法电脑插网线 │                 │ 话机/电脑(申请者)│
 └──────┬───────┘                 └──────┬───────┘
        ▼                                ▼ ① EAPOL
 ┌──────────────┐                 ┌──────────────┐  ①EAPOL  ┌────────────┐
 │ 交换机端口直通 │                 │ 交换机(认证者) │◄────────►│ RADIUS服务器 │
 └──────┬───────┘                 └──────┬───────┘  ②RADIUS └────────────┘
        ▼                                ▼ ③ 认证通过才放行
 ┌──────────────┐                 ┌──────────────┐
 │ 内网/服务器直达│                 │ 内网/服务器    │
 └──────────────┘                 └──────────────┘
 无认证·任意设备直入内网            认证通过才授权端口放行
```

## 二、核心三件套：谁在把关？

| 角色（英文） | 类比 | 实际设备 | 职责 |
|---|---|---|---|
| 申请者 Supplicant | 刷工牌的人 | IP 话机、电脑、手机 | 发起认证，提供身份凭证（用户名/密码/证书） |
| 认证者 Authenticator | 闸机/保安 | 交换机、AP（无线） | 不拍板，只负责"收凭证→转发→按结果开/关端口" |
| 认证服务器 Auth Server | 后台安保中心 | RADIUS 服务器（FreeRADIUS / ISE / NPS） | 查数据库，最终决定"放行"还是"拒绝" |

- **关键理解**：认证者（交换机）本身**不存储密码、不做最终判断**，只是"传话的闸机"——把凭证用 RADIUS 协议转给后台服务器，服务器说"OK"才开门。这正是核心设计：**认证决策集中、接入控制分布**。

### 两种协议封装

```
 申请者              认证者               认证服务器
Supplicant ──EAPOL──► Authenticator ──RADIUS──► Auth Server
IP话机/PC            交换机/AP(转发)      RADIUS 最终拍板
带凭证(身份)          (链路层封装)         (UDP 1812)

EAPOL 封装（二层，交换机内部）        RADIUS 封装（跨网段）
┌─────────────────────────────┐   ┌─────────────────────────────┐
│ 目的MAC│源MAC│类型=0x888E    │   │ UDP头 │ RADIUS头             │
│ EAP 数据(Identity/Response) │   │ User-Name / User-Password   │
└─────────────────────────────┘   └─────────────────────────────┘
 申请者与交换机之间的二层帧           申请者凭证藏在 RADIUS 属性里
```

- 申请者 ⇄ 认证者：EAP 报文封装在 **EAPOL**（EAP over LAN）帧里，只跑二层，**不依赖 IP**。
- 认证者 ⇄ 服务器：EAP 报文再封装进 **RADIUS** 协议的 Attribute 里，走 **UDP 1812** 端口。
- **注意**：EAPOL 不依赖 IP，意味着话机在**还没拿到 IP 地址**时就能开始认证——这正是它比"Web 认证"更早、更安全的原因：网络层还没通，门禁已经在工作了。

## 三、认证流程全解析：一次"刷工牌"的 8 步

以最常见的 **EAP 中继模式**（交换机把 EAP 原样透传给 RADIUS，由服务器选择认证方式）为例：

```
① 链路接通：话机插线，端口 UP，但处于【未授权 Unauthorized】状态，
            仅放行 EAPOL 流量（拿不到 IP、无法访问业务网络）
        ▼
② 发起认证：话机发 EAPOL-Start，或交换机主动发 EAPOL-Identity 请求
            （申请者 ⇄ 认证者，EAPOL 二层帧）
        ▼
③④ 身份交互：交换机把 EAP 封装进 RADIUS 转发服务器 →
            服务器回 Access-Challenge（质询）（RADIUS / UDP 1812）
        ▼
⑤⑥ 凭证验证：话机回密码/证书（EAP-Response）→ 交换机透传 →
            服务器校验（查库/验证书）；挑战-响应可能多轮（如 PEAP 的 TLS 握手）
        ▼
⑦ 结果下发：服务器回 Access-Accept（含 VLAN、ACL 等授权属性）→
            端口变为【已授权 Authorized】，可附带语音 VLAN ID、ACL、会话超时等
```

**举例（话机用 EAP-MD5 认证）**：
1. 话机插线，端口未授权；2. 话机发 EAPOL-Start；3. 交换机回 EAP-Identity 问"你是谁"→ 话机答 user=phone01；4. 服务器发 Challenge（随机挑战值）；5. 话机用密码对挑战值做 MD5 哈希，回 Response；6. 服务器自己算一遍哈希比对 → 一致；7. 回 Access-Accept，附带"语音 VLAN=10"；8. 交换机把端口划入 VLAN10，话机才去发 DHCP 拿 IP、注册 SIP。**全程未认证前，话机连 IP 都拿不到。**

## 四、EAP 协议家族：认证方式怎么选？

802.1X 只是"框架"，真正的认证逻辑由 **EAP（可扩展认证协议）类型**决定：

| EAP 类型 | 认证凭证 | 安全性 | 部署复杂度 | VOIP 适用场景 |
|---|---|---|---|---|
| EAP-MD5 | 用户名+密码（哈希） | 低（易受中间人/重放） | 最简单 | 内网可信环境、快速试点 |
| EAP-TLS | 客户端+服务器双向证书 | 最高（证书不可逆） | 高（需 PKI 体系） | 高安全要求的金融/政府 |
| PEAP | 服务器证书+用户密码 | 高（密码在加密隧道内） | 中 | **最常用**，话机+域账号 |
| EAP-TTLS | 服务器证书+内部任意凭证 | 高 | 中 | 需对接老式认证后端 |

```
安全性 ↑  ──────────────────────────────►
部署成本 ↑ ◄──────────────────────────────
┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
│ EAP-MD5  │ │  PEAP    │ │ EAP-TTLS │ │ EAP-TLS  │
│ 密码哈希  │ │服务器证书 │ │服务器证书 │ │ 双向证书  │
│ 安全性低  │ │ +密码    │ │+内部凭证 │ │安全性最高 │
│ 部署简单  │ │ 安全性高  │ │ 安全性高 │ │ 部署复杂  │
│ 测试/可信 │ │★VOIP最常用│ │对接老后端│ │金融/政府  │
└──────────┘ └──────────┘ └──────────┘ └──────────┘
        实践首选：PEAP = 安全与易部署的平衡点
```

**选型建议**：
- **PEAP**：VOIP 与企业网最平衡的选择——只需服务器证书（保护密码），话机配账号密码即可，绝大多数 IP 话机原生支持。
- **EAP-TLS**：安全性最高，但需给每台话机发证书，适合"机器身份"强绑定场景。
- **EAP-MD5**：仅建议测试或孤立可信环境，生产环境慎用。

## 五、VOIP 实战：话机 802.1X + 语音 VLAN

典型拓扑：**话机下挂 PC**，一根网线同时跑语音和数据，两者都要各自认证。

### 5.1 主机模式：一个端口能容纳几个设备？

端口的 **host-mode（主机模式）**决定"一个端口容纳几个客户端、按什么维度划分"：

| 主机模式 | 端口容纳能力 | VOIP 适用性 |
|---|---|---|
| Single-Host 单主机 | 仅允许 1 个客户端，话机与 PC 无法共存 | ✗ 不适用多设备场景 |
| Multi-Domain 多域 | 1 个语音域（话机）+ 1 个数据域（PC)，各自认证 | ✓ 话机下挂 PC 的经典方案 |
| Multi-Auth 多认证 | 多个客户端各自认证（可含多台数据终端） | ✓ 灵活，适合端口下再接小交换机 |
| Port-Based 基于端口（老式） | 任一客户端认证通过即整端口开放 | ⚠ 不安全：PC 过了话机免认证 |

**两个常被混淆的维度**：
- ① 容纳几个设备 → 由 host-mode 决定；
- ② 设备怎么证明身份 → 另一条线：支持 802.1X 的话机/PC 走 EAP 认证；老旧话机、打印机等不支持的设备可用 **MAB（MAC 旁路认证）**以 MAC 地址当账号做补充认证。两者正交：Multi-Domain 端口上话机走 802.1X、旁边的打印机走 MAB，互不影响。

### 5.2 认证失败怎么办？三类"兜底 VLAN"

| 类型 | 触发条件 | 作用 |
|---|---|---|
| Guest VLAN（访客 VLAN） | 认证失败 / 不支持 802.1X | 放入受限网络（仅上网，隔离内网） |
| Auth-Fail VLAN（认证失败 VLAN） | 凭证错误 | 区分"设备故障"与"无 802.1X 客户端" |
| Critical VLAN（应急 VLAN） | RADIUS 服务器全部不可达 | 让话机先进入应急 VLAN 保障通信 |

**VOIP 最佳实践**：话机用 802.1X（PEAP）认证，认证成功后由 RADIUS 下发的**隧道属性（Tunnel-Private-Group-ID）**自动把它划入语音 VLAN；PC 在数据 VLAN 单独认证。话机拿到语音 VLAN 后才发 DHCP、注册 SIP。即使 RADIUS 临时宕机，也可配置 Critical VLAN 让话机先通、事后补认证，避免全员"打不了电话"。

```
        VOIP 组网中的 802.1X：话机 + PC 各自认证
 ┌─────────┐ EAPOL ┌──────────────────┐ RADIUS ┌──────────────┐
 │ IP 话机  │──────►│ 接入交换机         │───────►│ RADIUS 服务器 │
 │(语音申请)│      │ 认证者+语音VLAN    │        │ 认证+授权     │
 ├─────────┤      │ Multi-Auth端口     │        │ 查账号库      │
 │ 办公 PC  │──────►│ 话机→VLAN10       │        │ 下发语音VLAN  │
 │(数据申请)│ EAPOL│ PC→VLAN20         │        └──────────────┘
 └─────────┘      └──────────────────┘

 ✔ 认证成功                          ⚠ 认证失败 / 服务器宕机
 话机→VLAN10(语音)→DHCP→SIP注册       话机→Guest VLAN(受限) 或
 PC→VLAN20(数据)→正常上网              Critical VLAN(应急通信)
 RADIUS下发 Tunnel-Private-Group-ID=10  绝不裸奔进内网，但保基本可用
 语音与数据逻辑隔离，各凭凭证入门         管理员后台可查失败原因
```

## 六、排错实战：话机卡在"正在认证"

**现象**：话机启动后一直显示"正在认证"或反复重启，拿不到 IP，无法注册。

**排查四步**：
1. **看凭证**：话机里配的 802.1X 账号/密码是否与 RADIUS 一致？常见是密码输错或账号被禁用。
2. **看端口模式**：交换机端口是否 `dot1x port-control auto`？若为 `force-authorized` 则根本不过认证；若为 `force-unauthorized` 则永远不通。
3. **看服务器连通**：ping radius-server 通吗？UDP 1812 是否被防火墙挡？`show radius statistics` 看有无请求发出/响应收回。
4. **看 EAP 类型匹配**：话机配的 PEAP，服务器却只开 EAP-TLS？类型不一致直接拒绝，抓包可见 Access-Reject。

**一句话口诀**：先查"账号对不对"，再查"端口开没开"，三查"服务器通不通"，四查"类型匹不匹配"。

**注意**：别让 RADIUS 单点故障拖垮全网。生产环境务必部署**至少两台 RADIUS（主+备）**，并配置 Critical VLAN——当服务器都不可达时，交换机能让话机先进入应急 VLAN 保障通话，而不是全员掉线。VOIP 网络"可用性"和"安全性"同样重要。

## 总结：全文知识点速查

| 概念 | 一句话 | 作用 |
|---|---|---|
| 802.1X | 基于端口的网络接入控制标准 | 设备联网前先认证"你是谁" |
| Supplicant 申请者 | 想进门的人（话机/PC） | 发起认证、提供凭证 |
| Authenticator 认证者 | 闸机（交换机/AP） | 转发凭证、按结果开关端口 |
| Auth Server 认证服务器 | 后台安保中心（RADIUS） | 最终决定放行/拒绝 |
| EAPOL | 二层封装 EAP（不依赖 IP） | 申请者与交换机之间传凭证 |
| RADIUS | UDP 1812 封装 EAP | 交换机与服务器之间传凭证 |
| EAP-MD5/TLS/PEAP/TTLS | 不同认证方式 | 平衡安全与部署成本 |
| Multi-Auth 多认证 | 一端口多设备各自认证 | 话机+PC 同时准入 |
| Guest/Critical VLAN | 认证失败/服务器宕机兜底 | 受限访问或应急通信 |
