## 〇、引入：经典故障场景

**真实场景**：
- 内网 SIP 话机 `192.168.1.100` 注册到公网 SIP 服务器 `sip.example.com`（203.0.113.50）
- 注册成功，但一打电话就**"单通"**——对方听得到你，你听不到对方，或根本建立不了通话

**根因**：NAT 只处理"由内向外"发起的连接，而 RTP 媒体流是**从外向内**推送的，被 NAT 直接丢弃。

## 一、NAT 是什么？先搞懂"墙"在哪里

### 1.1 NAT 的本质：地址翻译
- NAT = Network Address Translation，运行在**路由器/防火墙**上
- 核心功能：**把内网私网 IP 替换成公网 IP**，让内网设备访问互联网
- **为什么需要 NAT**：IPv4 仅约 43 亿个地址，ISP 只给路由器分一个公网 IP，内网设备共享这一个公网 IP 出网

```
        内网（私网）                      公网（Internet）
  ┌─────────────────────────┐      ┌──────────────────────┐
  │ 内网PC   192.168.1.100   │      │                      │
  │ SIP话机  192.168.1.150   │      │  SIP服务器 203.0.113.50│
  │ 内网PC2  192.168.1.200   │      │  Web服务器 203.0.113.80│
  │      │                   │      │          ▲           │
  │   交换机/局域网            │      └──────────│───────────┘
  └──────│──────────────────┘                 │ 翻译成公网
         │                            ┌───────┴────────┐
         └────私网地址────────────────▶│   NAT 路由器    │
                                     │ 公网侧 203.0.113.1│
                                     │ 内网侧 192.168.1.1│
                                     └───────┬────────┘
                                             │
                                     NAT 转换表
                                ┌──────────────────────────┐
                                │ 192.168.1.100:5060        │
                                │      → 203.0.113.1:10001  │
                                │ 192.168.1.150:5060        │
                                │      → 203.0.113.1:10002  │
                                │ 192.168.1.200:8080        │
                                │      → 203.0.113.1:10003  │
                                └──────────────────────────┘
```

### 1.2 核心规则：只允许"由内向外"
- NAT 维护**转换表**，记录"内网 IP:端口 ↔ 公网 IP:端口"映射
- **只为内网主动发起的连接创建映射**；外网主动进来的连接，查不到映射→**直接丢弃**
- 类比：公司前台——内部打出可转接并记录；外部直接打进"找工位100的员工"，前台不知道怎么转，直接拒绝

**举例**：话机 `192.168.1.150:5060` 注册，NAT 创建映射 `→ 203.0.113.1:10002`，SIP 服务器看到的是公网地址可回包。但 SIP 消息里 **SDP 写的是私网地址 192.168.1.150**，服务器往这个地址发 RTP → 公网不可达 → **媒体建立失败**。

## 二、NAT 的四种类型（RFC 3489，穿透难度递增）

```
① Full Cone（全锥形）· 最宽松          ② Restricted Cone（限制锥形）
  内网:5060 ↔ 映射:10001                  内网:5060 ↔ 映射:10001
     ▲   │                                ▲   │
  A B C 任何外部主机均可访问 ✓          A ✓  仅内网联系过的 IP 可访问
                                        B ✗  C ✗

③ Port Restricted Cone（端口限制锥形）  ④ Symmetric（对称型）· 最严格
  内网:5060 ↔ 映射:10001                  内网:5060 → 目标A :10001
  A:同端口 ✓  A:异端口 ✗                 内网:5060 → 目标B :10002
  主机C ✗  来源IP+端口都要匹配            每个目标分配不同端口
                                        STUN 探测到的端口对外无效 ✗
```

| 类型 | 映射规则 | 外部访问 | STUN 可穿透 |
|---|---|---|---|
| 全锥形 Full Cone | 同一内网端口→固定公网端口 | 任何外部主机均可 | ✅ 容易 |
| 限制锥形 Restricted | 同上 | 仅内网联系过的 IP | ✅ 可以 |
| 端口限制锥形 | 同上 | 仅内网联系过的 IP+端口 | ✅ 可以 |
| 对称型 Symmetric | **不同目标→不同公网端口** | 仅对应目标的 IP+端口 | ❌ 不行 |

> **关键结论**：前三种（锥形）可用 STUN 穿透——内网端口在公网侧的映射端口是固定的，STUN 能探测到；对称型对每个目标分配不同端口，STUN 探测结果对其他主机无效，**只能用 TURN 中继**。

## 三、VOIP 中的 NAT 问题：信令 + 媒体双重受阻

```
问题① SIP 信令：SDP 携带私网地址
 话机A(内网) ──INVITE──▶ NAT ──▶ SIP服务器 ──▶ 话机B(公网)
 192.168.1.150          203.0.113.1  203.0.113.50   203.0.113.60
 SDP: c=IN IP4 192.168.1.150  ← 私网地址！
 话机B 往 192.168.1.150 发 RTP → 公网不可达，媒体丢失 ✗

问题② RTP 媒体：外网→内网被 NAT 丢弃
 话机A(监听RTP:5004)    NAT无5004端口的内→外映射
   ◀───RTP被丢弃✗──NAT◀───RTP─── 话机B(公网):5004
   ────A→B的RTP能出去✓──（NAT自动创建映射）──▶
 结果：单向通话（A听到B，B听不到A）或完全无法通话
```

**两个核心问题**：
1. **SDP 私网地址**：INVITE 的 SDP 中 `c=IN IP4 192.168.1.150` 是内网地址，对端无法路由
2. **RTP 单向/丢失**：即使 SDP 被修正，RTP 从外网回内网时 NAT 没有端口映射 → 丢包
   - 根因：NAT 只允许"内→外"，RTP 通常是"外→内"推送

## 四、STUN / TURN / ICE：穿透三板斧

```
阶段① STUN ── 探测公网映射地址
 话机A ──①请求(从:5060出)──▶ STUN服务器(203.0.113.10)
      ◀─②响应:"你的公网地址是 203.0.113.1:10001"─
 ✓ 话机得知自己的公网映射地址 → 写入 SDP

阶段② TURN ── 中继转发（对称NAT的兜底）
 话机A ─③→ TURN服务器 ─④→ 话机B
      ◀─⑥     (公网中继)  ◀─⑤
 ⚠ 所有媒体经中继，增加延迟和带宽消耗，但 100% 可达

阶段③ ICE ── 智能选择最优路径
 收集候选地址 → 优先级排序 → 连通性检测 → 选择最优路径
 ┌──────────────┬───────────────┬──────────────┐
 │ 主机地址(最高) │ STUN反射地址(中) │ TURN中继地址(兜底)│
 └──────────────┴───────────────┴──────────────┘
 优先尝试直连 → 失败用STUN → 最后才走TURN中继
```

### 4.1 STUN：探测公网地址
- Session Traversal Utilities for NAT
- 内网设备问 STUN 服务器"你在我眼里是什么地址"，返回 NAT 映射后的公网 IP:端口
- 话机将其写入 SDP 的 `c=` 行和 `m=` 行，对端即可回发 RTP
- **举例**：话机 A（192.168.1.150）向 STUN 服务器（203.0.113.10）发请求，NAT 映射 `192.168.1.150:5060 → 203.0.113.1:10001`，服务器在响应中返回该地址

### 4.2 TURN：中继兜底
- Traversal Using Relays around NAT
- STUN 失败时（典型为对称型 NAT），所有媒体经 TURN 服务器中继
- 代价：**延迟增加 + 服务器带宽消耗**；优点：**100% 保证可达**

### 4.3 ICE：智能选路框架（不是独立协议，是框架）

| 步骤 | 动作 | 说明 |
|---|---|---|
| 1. 收集候选地址 | 主机地址 + STUN 反射地址 + TURN 中继地址 | 三种，优先级从高到低 |
| 2. 优先级排序 | 主机 > 反射 > 中继 | 直连最优，中继最差 |
| 3. 连通性检测 | 双方互发 STUN Binding 请求 | 测试每对候选地址可达性 |
| 4. 选择最优路径 | 取优先级最高的可达路径 | 优先直连，不通才中继 |

## 五、SIP NAT 穿透五种方案对比

```
┌──────────┬──────────┬──────────┬──────────┬──────────┐
│   STUN   │   TURN   │   ICE    │ SIP ALG  │   SBC    │
│探测公网地址│ 中继转发  │智能选路框架│网关深度改写│会话边界控制│
├──────────┼──────────┼──────────┼──────────┼──────────┤
│原理:问STUN│原理:所有RTP│原理:STUN+ │原理:NAT网关│原理:专用设备│
│"我是谁"   │经服务器中继│TURN自动选优│改写SDP地址│ B2BUA代理 │
│✓零中继延迟│✓100%可达 │✓智能适配  │✓终端零配置│✓功能全面  │
│✓带宽省    │✓兜底方案  │✓兼容所有NAT│✓透明处理  │✓运营商级  │
│✗对称NAT无效│✗延迟增加 │✗实现复杂  │✗兼容性差  │✗成本高    │
│✗需公网STUN│✗带宽消耗大│✗检测耗时  │✗常有Bug  │✗部署复杂  │
├──────────┼──────────┼──────────┼──────────┼──────────┤
│推荐:首选  │推荐:兜底  │推荐:最佳实践│推荐:慎用  │推荐:企业级 │
└──────────┴──────────┴──────────┴──────────┴──────────┘
   小型部署/测试   对称NAT环境   通用最佳实践   路由器自带   运营商/大型
```

> 💡 **实际推荐组合**：ICE（STUN 优先 + TURN 兜底）= 兼顾效率与可达性；企业级部署加 SBC，可彻底解决信令和媒体的 NAT 穿透问题。

**部署建议**：
- 小型/测试环境：话机侧配 STUN 即可，成本低
- 生产环境：配 ICE（STUN + TURN），确保对称 NAT 用户也能通
- 企业/运营商：部署 SBC，服务器侧统一处理穿透，终端零配置
- SIP ALG：路由器自带但 Bug 多，**建议关闭**，改用上述方案

## 六、NAT 穿透故障排错流程

```
                 VOIP 单通 / 无媒体
                        │
        ① 话机是否注册成功？（查话机状态 / SIP服务器日志）
                        │
              < 注册成功？信令可达？>
                   │否          │是
     检查5060端口 ────┘          ▼
     NAT/防火墙        ② 抓包看 SIP INVITE 的 SDP
                        （c= 行是公网IP还是私网IP？）
                                 │
                      < SDP 地址是公网？ >
                       │私网地址        │是
        → 开启 STUN ────┘             ▼
        → 或配 SBC 改写SDP   ③ 抓包看 RTP 是否双向？
                                （tcpdump/wireshark 过滤 rtp）
                                        │
                                < RTP 双向？ >
                                        │单向
                                  → 对称NAT？配 TURN 中继
```

排错主线：**注册 → SDP 地址 → RTP 方向，逐层定位**
