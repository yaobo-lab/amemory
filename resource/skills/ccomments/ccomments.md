# C 函数 Doxygen 注释整理

用户通过以下形式调用本 Skill：

```text
/ccomments <目标目录>
```

例如：

```text
/ccomments src/business/alarm
```

将用户提供的目录作为本次唯一处理范围。

## 输入检查

1. 从用户消息中提取目标目录。
2. 如果没有提供目录，询问用户需要处理哪个目录，不要猜测路径。
3. 确认目录存在后再开始修改。
4. 递归处理目标目录中的 `*.c` 和 `*.h` 文件。
5. 默认跳过第三方代码、自动生成代码、构建产物和目标目录之外的文件。
6. 如果目标目录属于第三方或自动生成目录，修改前先向用户确认。

## 处理对象

检查并整理以下对象：

1. 头文件中的公共函数声明。
2. C 文件中的公共函数定义。
3. C 文件中的 `static` 私有函数。
4. 函数指针和回调类型。
5. 已有函数注释。
6. 缺少注释的函数。

不要只处理公共 API，也不要只补充 `@brief`。

即使公共函数已经在头文件中声明，也要检查其 `.c` 文件中的函数定义，并补充完整的函数注释。

## 统一格式

函数注释统一使用 Doxygen 风格：

```c
/**
 * @brief 函数用途。
 *
 * @param parameter 参数含义。
 * @return 返回值含义。
 */
```

多参数函数按照函数签名中的参数顺序逐项说明：

```c
/**
 * @brief 读取并整理一帧音频数据。
 *
 * @param data 调用方提供的输出缓冲区。
 * @param capacity 输出缓冲区容量，单位为字节。
 * @param length 接收实际写入长度，单位为字节。
 * @param timeout_ms 等待超时，单位为毫秒。
 * @return 保留超时、设备失效等具体结果，供 HAL 决定后续处理。
 */
```

## `@brief` 规则

1. 不得修代码的内容
2. 如果函数已经有注释：
    - 保留原注释文本和原有语义；
    - 将原注释文本作为 `@brief` 的内容；
    - 不擅自重写或删除原注释表达的信息；
    - 在此基础上补充缺失的 `@param` 和 `@return`。
3. 如果函数没有注释：
    - 阅读函数实现、声明和必要的调用位置；
    - 根据实际行为编写简洁准确的 `@brief`；
    - 不编造代码中不存在的行为。
4. `@brief` 说明函数做什么，不逐行复述实现

已有注释的转换示例：

```c
// 将闹钟领域模型转换为调度器使用的中立触发项。
```

转换为：

```c
/**
 * @brief 将闹钟领域模型转换为调度器使用的中立触发项。
 *
 * @param alarm 待转换的闹钟领域模型。
 * @return 包含闹钟状态快照的调度触发项。
 */
```

## `@param` 规则

1. 每个具名参数必须有且只有一个对应的 `@param`。
2. `@param` 中的参数名必须与函数签名完全一致。
3. `@param` 的排列顺序必须与函数签名一致。
4. 参数说明应根据实际情况包含：
    - 参数用途；
    - 输入、输出或输入输出语义；
    - 容量、长度或时间的单位；
    - 是否允许为 `NULL`；
    - 有效取值范围；
    - 特殊值含义。
5. 不要使用“参数”“数据”等无法提供有效信息的描述。
6. 输出参数应明确说明结果如何写回，例如：

```c
 * @param length 接收实际写入长度，单位为字节。
```

7. 输入输出参数应明确说明原值用途和结果写回方式，例如：

```c
 * @param value 待增加一个月的本地日历时间，结果原位写回。
```

8. 当前未使用的回调上下文也要说明，例如：

```c
 * @param context 调度器回调上下文，当前未使用。
```

9. 无参数函数不添加 `@param`。

## `@return` 规则

1. 所有非 `void` 函数必须有 `@return`。
2. `@return` 应覆盖函数中有意义的返回情况，包括：
    - 成功值；
    - 失败值；
    - 特殊值；
    - 错误码；
    - 返回数量或长度的单位；
    - 返回指针的所有权和有效期。
3. `bool` 返回值应明确 `true` 和 `false` 的含义：

```c
 * @return 初始化成功返回 true，否则返回 false。
```

4. 返回编号或错误值时，应明确特殊值：

```c
 * @return 成功返回分配的闹钟编号，失败返回 -1。
```

5. 回调固定返回某个值时，应如实说明：

```c
 * @return 固定返回 0。
```

6. `void` 函数不添加 `@return`。

## 回调类型

函数指针和回调类型同样补充参数和返回值说明：

```c
/**
 * @brief 领域对象到期处理器。
 *
 * @param owner_id 到期的领域对象编号。
 * @param context 注册处理器时提供的上下文。
 */
typedef void (*business_trigger_owner_due_handler_t)(
    int32_t owner_id,
    void *context);
```

回调返回类型不是 `void` 时，必须添加 `@return`。

## 修改约束

1. 只修改注释。
2. 不修改函数逻辑或函数签名。
3. 不修改类型、宏、include 或构建配置。
4. 不重命名文件、函数、参数或类型。
5. 不调整与注释无关的代码格式。
6. 不顺带修复其他问题。
7. 不覆盖或撤销用户已有修改。
8. 函数内部用于解释算法、锁、生命周期或特殊约束的普通注释，不强制转换为 Doxygen。
9. 如果编辑器保存时自动格式化整个文件，必须恢复与注释无关的格式变化，确保最终差异只包含注释。
10. 遵守项目中其他已启用的架构、编码规范和安全 Skill；发现无关历史问题时只报告，不顺带修改。

## 完成检查

修改完成后，逐个函数核对：

1. 是否存在 `@brief`。
2. 每个具名参数是否都有对应的 `@param`。
3. `@param` 参数名是否与函数签名完全一致。
4. `@param` 顺序是否与函数签名一致。
5. 每个非 `void` 函数是否都有 `@return`。
6. `@return` 是否覆盖成功、失败和特殊返回值。
7. `void` 函数是否避免了无意义的 `@return`。
8. 无参数函数是否避免了无意义的 `@param`。
9. 已有注释文本是否被保留为 `@brief`。
10. 最终差异是否只包含注释。

如果项目使用 Git，至少执行：

```bash
git diff --check
git diff -- <目标目录>
```

如果编辑器提供诊断，检查所有修改文件是否存在错误或警告。

对于纯注释修改，通常不需要运行完整构建或业务测试，但必须在结果中说明未运行的原因。

## 完成报告

完成后简要报告：

1. 修改了哪些文件。
2. 整理了多少个函数和回调类型。
3. 是否为全部参数补充了 `@param`。
4. 是否为全部非 `void` 函数补充了 `@return`。
5. 是否存在无法从代码中准确判断的语义。
6. 执行了哪些检查。
7. 是否发现与本次注释修改无关的历史问题。
