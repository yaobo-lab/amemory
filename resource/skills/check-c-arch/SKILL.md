# C 项目架构检查

对当前项目执行一次只读的全仓架构审查，找出违反项目架构原则的具体位置。不要只运行脚本就结束；脚本是第一轮证据，必须继续检查脚本无法可靠识别的符号、类型、回调和 CMake 关系。

## 默认行为

- 用户只执行 `/check-c-arch` 时，检查整个当前仓库。
- 用户明确给出文件或目录时，可以缩小检查范围，但仍检查相关公共头、调用方和 CMake 目标。
- 默认不修改源码、构建文件或规范。只有用户随后明确要求修复时才动手。
- 不审查第三方库、生成代码、预编译 SDK 和纯静态资源；若它们被一方代码错误依赖，则检查该依赖边界。
- 不把普通格式、拼写或个人风格偏好当作架构违规。

## 必读规则

开始检查前完整阅读：

1. [分层架构](references/architecture.md)
2. [架构审查清单](references/audit-checklist.md)
3. 涉及驱动、平台文件或 CMake 时阅读 [平台、文件与构建](references/platform-build.md)

规则冲突时，以仓库当前的 `docs/归档文件/嵌软代码质量建设规范-AI版本.md` 和实际构建配置为准；报告中明确说明冲突，不自行发明新规则。

## 执行步骤

### 1. 确认项目和检查范围

1. 定位仓库根目录及 `src`、根 `CMakeLists.txt`、子目录 CMake 文件。
2. 确认是否存在 `src/app`、`src/business`、`src/hal`、`src/drivers`、`src/pkg`；缺失目录不算违规。
3. 列出一方 `.c`、`.h` 和相关 CMake 文件。识别第三方、生成文件和平台 SDK，避免误报。
4. 读取 `git status` 仅用于区分未提交修改；不得重置、覆盖或清理用户工作。

### 2. 运行全仓静态检查

从仓库根目录运行：

```bash
python3 .agents/skills/check-c-arch/scripts/check_c_arch.py
```

若用户限定范围，将路径逐个传入脚本。保留脚本输出中的文件、行号和原因。脚本失败时继续人工核实，不要把正则扫描结果直接当作最终结论。

脚本覆盖：

- 直接 `#include` 越层；
- drivers 同级驱动单元依赖；
- 非 app 层的 LVGL include/type 泄漏；
- app 对废弃 `src/include` 的依赖；
- 宏定义头和模块级 `_def.h` 的明显越界。

### 3. 人工检查编译期依赖

检查头文件、符号调用、公开类型、回调签名、宏引用和链接目标，而不只检查 include：

- `app` 是否直接调用或链接 `hal`、`drivers`、平台 SDK；
- `business` 是否依赖 `app`、`drivers`、`resource` 或 LVGL；
- `hal` 是否反向依赖 `app`/`business` 或泄漏 driver/SDK 类型；
- `drivers` 是否依赖 `hal`、其他独立驱动单元或产品业务；
- `pkg` 是否承载产品业务、特定硬件配置或反向依赖产品层；
- CMake 的 `target_link_libraries`、`target_include_directories`、源码聚合是否建立反向或跨层通道。

对疑似违规追到定义和调用点，确认不是注释、字符串、测试替身、条件编译死分支或同名符号后再报告。

### 4. 人工检查职责与接口边界

按审查清单逐项核实：

1. UI/LVGL、领域用例、持久化、平台无关能力、平台实现是否放在正确层。
2. `app` 的硬件访问是否遵循 `app → business → hal → drivers`。
3. API 请求、结果、状态、事件和回调类型是否由提供接口的一层拥有。
4. 公共头是否泄漏 LVGL、平台 SDK、driver 私有类型或不必要的 `_priv.h`。
5. 下层是否通过包含上层头或直接调用上层函数来反向通知。
6. driver 错误是否由 hal/business 分层映射，而不是原样泄漏或由 driver 决定产品策略。
7. business 到 app 的通知是否由 business 定义事件；非 UI 发布线程是否经 `ui_app_notify_post()` 后再操作 LVGL。
8. 外部回调是否在持有内部锁时调用，借用载荷和注销生命周期是否存在明显风险。
9. 宏、接口容量和日志前缀是否由提供模块维护，消费方是否复制同值定义。
10. 平台实现命名、互斥选择和 driver 独立构建是否合理。

### 5. 审核证据并分级

只报告有可定位证据的问题。无法从静态代码确认的内容放入“待确认风险”，不得写成确定违规。

严重级别：

- **严重**：形成反向依赖/循环依赖、跨层直接控制硬件、非 UI 线程直接操作 LVGL、平台实现重复链接等可能导致错误行为或无法构建的问题。
- **高**：明确越层 include/符号/链接、公共 API 泄漏专用类型、driver 单元耦合、回调生命周期或锁边界违反契约。
- **中**：职责放错层、宏/私有头作用域扩大、构建目标公开过多内部目录、平台文件组织违反约定。
- **低**：尚未造成越层但持续扩展会破坏边界的结构性问题。不要用低级别填充普通代码风格问题。

## 输出格式

使用中文，先给结论，再给证据。若存在违规，按严重程度排序：

```markdown
# 架构检查结果

结论：不通过
检查范围：...
自动检查：命令及退出状态

## 汇总
| 严重 | 高 | 中 | 低 | 待确认 |
| --- | --- | --- | --- | --- |
| ... | ... | ... | ... | ... |

## 违规项
### ARCH-001 [高] app 直接依赖 HAL
- 位置：`src/app/example.c:42`
- 原则：`app` 只能依赖 `business` 和通用 `pkg`
- 证据：包含 `hal/example.h` 并调用 `hal_example_open()`
- 影响：UI 与硬件能力绑定，破坏替换和测试边界
- 最小修复：在 `business` 增加面向用例的接口，由 business 调用 HAL

## 待确认风险
- ...

## 已检查但未发现问题
- LVGL 隔离、CMake 链接方向、平台互斥选择等
```

如果没有确认的违规，结论写“通过”，仍列出检查范围、脚本命令、人工检查项和待确认风险。不得仅写“脚本通过”。

## 审查约束

- 每项违规必须包含可点击的项目相对路径和行号。
- 同一根因影响多个文件时合并为一项，并列出主要证据，避免刷屏。
- 区分当前未提交修改与已有代码，但全仓检查不能因为是历史问题就忽略。
- 给出最小合规方向，不在审查阶段直接重构。
- 如果因缺少平台依赖、生成文件或构建环境而无法验证，明确说明未验证内容，不猜测结果。
