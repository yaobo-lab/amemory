# 嵌入式 C 代码质量与分层架构

在完成用户请求的前提下，维护本仓库一方 C 代码的可读性、接口契约和单向架构。优先解决本次修改引入的问题；除非用户要求专项治理，不顺手迁移无关历史代码。

## 适用范围

- 适用：`src/app`、`src/business`、`src/hal`、`src/drivers`、`src/pkg` 及直接相关的 CMake 定义。
- 条件适用：`src/main.c` 涉及生命周期或分层目标装配时，检查它是否只承担入口职责。
- 不适用：第三方库、生成代码、预编译 SDK、纯图片/字体资源转换。
- 修改既有代码时以仓库配置和邻近代码风格为基准；与通用习惯冲突时，以本技能引用的项目约定为准。

## 按需读取参考

开始修改前，根据任务读取参考文件，不要凭记忆推断规则：

- 涉及目录归属、跨层类型、硬件调用、通知、LVGL 或链接方向：阅读 [分层架构](references/architecture.md)。
- 涉及 `.c`/`.h`、API、命名、返回值、错误、回调、宏、常量或日志：阅读 [C 代码与接口约定](references/c-code-quality.md)。
- 涉及新增/重命名文件、平台实现、驱动目录、CMake、构建或验证：阅读 [平台、文件与构建](references/platform-build.md)。
- 同时命中多个范围时读取对应的全部参考；架构审查应至少读取前两份。

## 执行流程

### 1. 确认修改边界

1. 阅读相关公共头、实现、私有头和 CMake 定义。
2. 搜索调用方、实现方、回调注册点、链接目标和同类模块。依赖不仅是 `#include`，还包括公开类型、直接符号调用、回调签名、宏引用和目标链接。
3. 区分本次新增问题与历史遗留问题。只修改完成任务所必需的文件。

### 2. 先判断职责所有者

按以下顺序决定代码位置：

1. UI 渲染、LVGL 对象、页面导航、UI 状态和 UI 线程调度属于 `app`。
2. 用例、业务校验、领域状态、重试/降级决策和业务事件属于 `business`。
3. 持久化、序列化和查询结果转换属于 `business/dal`；它仍受 `business` 依赖规则约束。
4. 与平台无关的硬件能力和中立类型转换属于 `hal`。
5. Linux、芯片、开发板或厂商 SDK 的具体操作属于 `drivers` 中按能力组织、可独立构建的驱动单元。
6. 只有与产品业务、UI 和特定硬件均无关的基础能力才属于 `pkg`。

若 `app` 需要硬件能力，路径必须是 `app → business → hal → drivers`。禁止为了少写一层接口而越层调用。

### 3. 先设计契约，再写实现

1. 由 API 提供层拥有请求、结果、状态、事件和回调类型。
2. 公共头只暴露调用方所需的中立 C 类型、常量和函数；不泄漏 LVGL、平台 SDK 或下层私有类型。
3. 仅表示成功/失败时返回 `bool`；需要区分原因时定义模块自己的 `_result_t`，并在层间映射。
4. 回调携带 `void* context`，并明确覆盖/多订阅、`NULL` 注销、线程、重入、载荷生命周期和锁边界。
5. 公共 API 使用 Doxygen 说明参数方向、单位、所有权、生命周期和返回语义；不要用注释重复显而易见的代码。

### 4. 实现时执行质量约束

- 使用根目录 `.clang-format`，保持 C11、4 空格、无 Tab，并保留合理的 include 分组。
- 文件、函数、类型、枚举和变量按所有者命名；新增文件作用域状态优先 `static`，沿用一方代码的 `g_` 前缀。
- 一个函数只承担一项职责；新增控制块嵌套不超过 4 层。重复两次时考虑提炼，超过三次应重构。
- 公共入口尽早校验参数和状态；重要返回值必须处理，有意忽略时显式 `(void)` 并确认降级可接受。
- 宏和常量按最小作用域放置，不在消费方复制同值定义；运行期日志使用 `LOGGER_*`，包含操作和结果且不输出秘密。
- 删除本次修改产生的废弃声明和实现；不保留注释掉的旧代码。

### 5. 重点检查线程与通知

业务状态更新 UI 时，通过 `business/notify` 同步发布由 `business` 拥有的事件。`app` 注册处理器；如果发布线程不是 UI 线程，处理器只复制必要数据并通过 `ui_app_notify_post()` 投递，最终只在 UI 线程操作 LVGL。调用外部回调前释放内部互斥锁。

### 6. 验证

1. 对修改过的 C/C++ 文件运行项目 `.clang-format`；避免格式化无关文件。
2. 新增或删除 `.c` 后重新执行 CMake 配置。
3. 运行受影响目标已有的测试或构建。
4. 对本次修改路径运行：

    ```bash
    python3 .agents/skills/embedded-layer-architecture/scripts/check_architecture.py <changed-file-or-directory> [...]
    ```

5. 仅在用户要求全仓库审查时省略路径。脚本只检查可静态识别的直接分层依赖、LVGL 泄漏和宏放置；仍须人工检查传递包含、公开符号、回调契约、条件编译和链接关系。

## 审查与交付

- 发现问题时，给出文件和行号、违反的具体边界、影响以及最小修复方向。
- 区分“本次修改引入”与“历史遗留”，不要把历史问题伪装成本次已修复内容。
- 没有发现问题时，说明人工检查了哪些边界，以及实际运行了哪些格式化、脚本、构建或测试命令。
- 不得仅因架构脚本通过就声称全部规范合规。
