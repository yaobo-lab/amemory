# 程序员笑话

根据用户指定的技术主题创作或选择一个简短笑话。笑点应让熟悉该主题的开发者容易理解，同时避免为了制造梗而给出明显错误的技术结论。

## 触发边界

- 仅当用户明确要求笑话、幽默内容，或直接点名 `dev-joke` 时使用。
- 用户正在提问、调试、审查或实现代码时，不要主动讲笑话，也不要用笑话代替技术答复。
- 用户指定主题、语言、风格或长度时优先遵守；未指定主题时，从常见开发主题中选择一个。
- 用户说“再来一个”时继续输出，但不得重复当前对话中已经讲过的笑话；优先更换笑点或主题。

## 输出规则

1. 默认只输出一个笑话，控制在一至三句话。
2. 直接给出笑话，不添加“好的”“给你讲一个”、标题、解析、免责声明或结束语。
3. 默认使用中文；用户使用其他语言或明确指定语言时，跟随用户。
4. 优先使用铺垫加包袱、术语双关、语义反差或开发场景反转，不把普通技术事实硬说成笑话。
5. 除非用户明确要求，不使用 Markdown 代码块、列表、表情符号或大段背景说明。
6. 不嘲讽具体个人或群体，不包含低俗、歧视、仇恨、暴力、政治或敏感灾难内容。

## 主题选择

可围绕以下主题创作：

- 编程语言：Rust 所有权与借用、C 内存、Python 缩进、Java 类型与运行时。
- 开发流程：Bug、调试、代码审查、测试、CI、需求变化和技术债。
- 工具与协作：Git、编辑器、终端、包管理和版本依赖。
- 基础设施：Linux、网络、DNS、容器、Kubernetes、监控和发布。
- 数据与设备：SQL、事务、缓存、嵌入式、串口和固件。

避免连续使用“在我机器上是好的”、`Oct 31 == Dec 25`、SQL 走进酒吧等高频老梗；只有用户明确要求经典程序员笑话时才优先选用。

## 质量检查

输出前快速确认：

- 是否只有一个清晰笑点。
- 是否符合用户指定主题。
- 是否足够简短且无需额外解释。
- 是否与当前对话中已输出的笑话不同。
- 是否不存在明显技术错误或不合适内容。
